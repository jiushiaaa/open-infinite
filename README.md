# Living Novel Engine

> 一个会自己生长、能被读者干预、角色可能反抗命运的 AI 小说世界。

Living Novel Engine 是一个探索型开源项目构想。它试图把小说从“被作者写完的静态文本”，变成一个持续运行、可以观察、可以干预、可以分叉、甚至会反向凝视读者的故事宇宙。

这个项目受到多智能体仿真、长篇网文状态管理、互动叙事、世界线理论，以及《第一玩家》中第九世界、第十世界、第十一世界罗瓦莎相关叙事机制的启发。它不会复刻任何原作设定，而是抽象其中的机制：高维观测、世界线、命运干预、主人公身份、人设约束、剧情修正、角色反抗。

## 一句话定位

不是读小说，而是进入一部正在活着的小说。

## 核心问题

传统小说的交互是：

```text
作者创造剧情 -> 角色执行剧情 -> 读者阅读结果
```

Living Novel Engine 希望变成：

```text
创作者设定世界规则 -> 角色自主行动 -> 读者观察或干预 -> 世界继续演化 -> 系统生成文本
```

它不是普通 AI 续写器。普通续写器的本质是“给一段文字，生成下一段文字”。Living Novel Engine 的本质是“把小说解析成一个可运行的世界，让读者影响这个世界，再由世界长出新的文字”。

## 为什么是文字小说

小说天然是低成本、高想象力的媒介。

3D 游戏要表现一次末日、神战、群星坠落，需要大量美术、动画、物理、特效与性能预算。但小说只需要一句文字，读者会在脑内完成最昂贵的渲染。

这意味着，一个“文字版开放世界”比 3D AI 世界更容易落地：

- 前端可以是阅读器、侧边栏、世界线树、关系图谱
- 核心交互可以全部通过文字完成
- 角色行动可以先以结构化事件推演，再渲染为章节正文
- 用户的想象力本身就是最强渲染引擎

## 典型使用场景

### 续写断更小说

用户导入一段已有文本，系统提取角色、世界观、伏笔、当前冲突与章节状态，然后在断更节点之后继续运行世界。

系统尝试回答：

```text
如果作者不再写了，这些角色自己会走向哪里？
```

### 拯救意难平

用户回到某个关键节点，注入一次干预：

- 让某个角色提前收到预警
- 让一封信没有丢失
- 让一个配角晚出门十分钟
- 让某个误会被提前揭开
- 让一个反派在黑化前收到一次善意

系统不会直接满足愿望，而是把干预作为世界变量注入。角色可能相信，可能怀疑，可能抗拒，也可能因为新的信息做出完全意外的选择。

### 平行世界线探索

同一本小说可以长出多条世界线：

```text
原作主线
├─ 师姐存活线
├─ 主角黑化线
├─ 女主提前觉醒线
├─ 反派洗白线
└─ 全员失败的暗黑线
```

每条世界线都有自己的状态、记忆、关系和章节历史。读者不是读一本书，而是在观察一个故事宇宙的多种可能性。

### 作者的大纲压力测试

作者可以把自己的设定和大纲导入系统，让角色自主推演：

- 如果主角第 5 章没有救下配角，第 80 章会怎样？
- 如果反派不是降智莽夫，而是隐忍谋略型，剧情会怎样？
- 如果女主知道了真相，她还会选择主角吗？
- 如果世界规则严格执行，爽点是否仍然成立？

## 来自《第一玩家》的机制启发

《第一玩家》里有几类机制与 Living Novel Engine 非常接近，适合转化为产品设计语言。

### 高维观测与低语

第九世界相关设定中，世界不是单纯的生活空间，而是被观测、被入侵、被变量影响的系统。高维存在不能总是直接下场，但可以通过低语、诱导、规则缝隙和间接投放影响人物。

对应到产品里：

- 读者不是直接改写结局，而是向世界投放变量
- 角色不一定知道读者存在，但会感知异常
- 干预越频繁，世界越容易产生“被高维触碰”的痕迹

### 多层世界与模拟

第九世界呈现了低维世界、模拟世界、程序化命运路径等结构。它启发我们把小说世界拆成多层：

```text
原作文本层
世界状态层
角色记忆层
模拟推演层
读者干预层
世界线分支层
```

用户看到的是章节正文，但系统真正维护的是一套可以反复推演和回滚的世界状态。

### 世界线与收束

第十世界相关机制把“世界线”变成核心叙事资产。不同世界线可以并行、错过、映射、融合，也可能因为某种选择被保留或牺牲。

对应到产品里：

- 每次重大干预生成新世界线
- 世界线不是普通存档，而是完整的故事分支
- 系统可以展示世界线差异、关键分歧点和角色命运变化
- 用户可以选择保留、继续、归档或对比某条世界线

### 创生者与故事作为世界法则

第十一世界罗瓦莎最重要的启发是：故事本身可以成为世界物理法则。角色拥有“人设”，事件拥有“剧本”，关键经历会成为故事材料，人物会争夺主人公、配角、反派等叙事位置。

对应到产品里：

- 每个角色都有可审计的人设约束
- 用户干预不能随意破坏角色逻辑
- 角色可以意识到自己被推向某个叙事身份
- 世界可以出现“剧情修正”机制，抵抗过强的外部改写

### 主人公身份与角色反抗

罗瓦莎里，“主人公”不只是光环，也可能是诅咒。被选中的人会被剧情裹挟，被要求承担戏份、命运和世界期待。

对应到产品里：

- 角色可以拒绝成为主角
- 配角可以争夺戏份
- 反派可以反抗自己的标签
- 被读者反复干预的角色可能质问读者
- 第四面墙不是彩蛋，而是长期交互后自然涌现的结果

## 三层交互

### 第一层：读者旁观

读者像看小说一样阅读，但每一章不是提前写死的，而是系统根据世界当前状态生成。

同一本小说，不同读者看到的剧情可能不一样。因为每个读者的世界状态、干预历史、角色关系、随机种子都不同。

```text
点击：时间流逝
系统：角色继续生活、交谈、行动、博弈
结果：生成下一章正文
```

### 第二层：读者干预

读者可以像神谕一样影响世界：

- 给主角一个梦境提示
- 让某个角色捡到一封信
- 改变天气、谣言、资源、危机
- 向某个角色低语一句话
- 投放一个新事件
- 延迟某个人出门十分钟
- 改变一条关键情报的传播路径

但角色不一定照做。因为每个角色有自己的性格、利益、记忆和命运惯性。

这点很重要：用户不是点选项决定剧情，而是向世界施加变量。

### 第三层：角色反抗

角色如果足够“活”，就不应该只是执行用户命令。

例如：

- 用户想强行让女主爱上反派，但女主根据记忆和人格拒绝
- 用户想让主角走爽文路线，但主角因为长期失败变得多疑和阴郁
- 用户不断干预世界，角色开始意识到命运被某种存在操控
- 用户希望所有人都活下来，但角色间的利益冲突仍然产生新的代价

角色可能逐渐感知到：

```text
为什么我总是在关键时刻被安排？
为什么我的选择会被一种外部力量扭曲？
你到底是谁？
你是读者、作者，还是神？
```

## 核心系统

### 1. 文本导入与世界锚定

从用户上传的章节中提取：

- 角色
- 地点
- 势力
- 时间线
- 未完成伏笔
- 关键冲突
- 人物关系
- 世界规则
- 当前章节状态

### 2. 角色 Agent

每个角色不只是名字，而是带有结构化状态的 Agent：

- 人设标签
- 长期记忆
- 当前情绪
- 目标与恐惧
- 对其他角色的关系
- 可接受与不可接受的行为边界
- 对读者干预的敏感度

### 3. 故事合约

故事合约是世界的法律：

- 战力不可随意越界
- 角色不能无理由 OOC
- 伏笔不能无故消失
- 世界观规则不能随意破坏
- 用户干预必须被世界合理消化

### 4. 干预引擎

干预引擎把用户输入转化成世界变量：

```json
{
  "type": "dream_hint",
  "target": "senior_sister",
  "content": "梦见自己死在城外竹林",
  "strength": "soft",
  "visibility": "character_only",
  "cost": "low",
  "risk": "timeline_divergence"
}
```

### 5. 剧情修正机制

当用户干预过强，系统不会简单接受，而会触发修正：

- 角色怀疑异常
- 世界规则要求代价
- 其他势力补位
- 时间线分裂
- 关键角色拒绝执行
- 系统提示干预违反人设或世界合约

### 6. 世界线浏览器

世界线浏览器用于展示：

- 原作主线
- 干预分支
- 分歧节点
- 角色命运对比
- 伏笔状态差异
- 世界线风险等级

### 7. 叙事渲染器

多 Agent 推演的原始结果是结构化事件，不是最终正文。叙事渲染器负责把它转成可读小说：

```text
推演事件 -> 情绪节奏 -> 章节结构 -> 网文正文 -> 摘要与状态提交
```

## 与 webnovel-writer 和 MiroFish 的关系

### webnovel-writer：故事规则与长篇记忆

`webnovel-writer` 可作为故事状态管理与写作生成层：

- 管理世界观、角色、势力、伏笔、章节大纲
- 维护长期记忆和故事状态
- 审查 OOC、战力越界、时间线冲突
- 把推演结果写成符合题材节奏的章节正文

### MiroFish：多智能体动态推演

`MiroFish` 可作为角色社会仿真层：

- 把角色和势力转成 Agent
- 模拟对话、冲突、结盟、背叛、误判
- 让剧情从多角色互动中涌现
- 评估用户干预后的世界反应

### Story Simulation Orchestrator：中间编排层

两者之间需要新增编排层：

- 选择本章参与角色
- 控制推演轮次和成本
- 注入读者干预
- 过滤违反故事合约的行为
- 提炼爽点、反转、伏笔和情绪高潮
- 将推演日志交给叙事渲染器

## MVP

第一版不做完整小说宇宙，只做“单本小说 + 少量核心角色 + 章节级干预”。

### MVP 功能

- 导入 3-10 章文本，或使用内置原创样例
- 自动提取 5-8 个核心角色
- 生成角色卡、关系图、当前冲突、未完成伏笔
- 用户选择一个关键节点
- 用户输入一次自由干预
- 系统生成 2-3 条后续世界线
- 用户选择一条继续阅读
- 保存世界线分支

### MVP 成功标准

- 用户能理解“不是选择分支，而是施加变量”
- 用户愿意为了拯救意难平或续写断更进行多次尝试
- 每条世界线之间有明显差异
- 角色不会无理由服从用户
- 生成正文能保持基本连贯和人设一致

## 版权与伦理边界

这个方向天然涉及用户上传文本、续写断更作品、生成平行世界线等敏感问题。项目需要明确边界：

- 优先支持原创文本、公版文本和用户拥有权利的文本
- 对受版权保护的商业小说，默认定位为本地个人探索，不鼓励公开分发生成内容
- 不声称生成内容代表原作者意图
- 不冒充原作者继续连载
- 分享世界线时应保留来源说明和版权提示
- 项目文档中引用具体作品时，只抽象机制，不复刻专有设定与表达

## Roadmap

### Phase 0：概念验证

- 内置原创短篇世界
- 手动配置角色卡和世界规则
- 支持一次干预
- 生成 2-3 条世界线结果

### Phase 1：文本导入与世界锚定

- 支持导入 3-10 章文本
- 自动提取角色、关系、地点、冲突
- 生成初始世界状态
- 可视化角色关系

### Phase 2：章节级推演

- 支持 3-8 个角色的单场景推演
- 支持多轮 Agent 行动
- 支持故事合约审计
- 支持章节正文渲染

### Phase 3：世界线系统

- 支持分支保存
- 支持回滚关键节点
- 支持世界线对比
- 支持角色命运变化摘要

### Phase 4：第四面墙

- 记录读者干预痕迹
- 计算角色异常感知
- 支持角色逐渐意识到高维干预
- 支持角色向读者发问或抵抗命运

### Phase 5：社区与分享

- 分享世界线摘要
- 分享角色命运变化
- 支持导出分支小说
- 支持原创世界模板市场
