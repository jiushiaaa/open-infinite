# LNE 支撑层与后置增强索引

> 用途：说明哪些能力已经作为支撑层收口、哪些只在明确触发时继续。本文不是当前默认路线；当前路线请读 `../memory.md`、`index.md` 和 `unfinale-world-sandbox-remodel-prd.md`。

## 1. 当前边界

当前默认主线是 **World Sandbox Loop / 小说世界沙盘体验深化**。后续增强只有在服务下列目标时才进入：

```text
世界会运行。
角色会自主。
角色会记得。
干预有后果。
角色可能反抗。
世界会代偿。
章节来自世界演化。
```

如果一项增强只是在增加 provider、Graph、检索评测、OpenAPI、发行、计费、工程健康面板或只读 checklist，默认不做。

## 2. 已收口支撑层

这些能力已经有 MVP、artifact、API、UI、CLI 或文档证据；它们保留为支撑层，不作为下一刀来源。

| 分组 | 已有能力 | 继续条件 |
| --- | --- | --- |
| 长篇底座 | ChapterBrief、分层记忆、canon ledger、entity alias、consistency audit、runtime memory | 长篇正文质量明显受限，且世界沙盘主线需要它们补强时 |
| 审计与健康 | Runtime Preflight、Projection Health、contract / guardrail / audit log、本地商业化边界 | 运行前后经常缺 artifact、状态不一致或需要正式入卷审计 |
| 读者/作者质量 | Reader Panel、Adversarial Revision Lab、Worldline Judge、Narrative Diagnostics | 需要支持当前 Reviewer、整章风格润色或真实语义编辑器时 |
| 设定资产 | MasterSetting、Cards Workspace、世界卡、角色卡、风格卡 | 作者长期维护设定，且需要卡片版本化或批量编辑 |
| 模型配置 | Provider/Cost、Model Configuration UX、LLM Profile Assignment、route matrix、usage 估算 | 多任务真实模型参数需要经常调整或做 A/B |
| 检索增强 | BM25、canon ledger、aliases、Prompt Budget Pack、失败样本、mock evaluation、百炼 embedding、Zilliz、百炼 reranker、hybrid vector opt-in | 真实失败样本持续证明默认 BM25 不够，且 hybrid vector replay 明显收益 |
| Graph/长期记忆评估 | GraphRAG/Zep trigger evidence、design pack、shadow compare、case matrix、provider boundary、offline replay、manual mock adapter review | 关系/因果/状态链持续错乱，并且已有证据链证明重型记忆收益 |
| 发行/本地体验 | Local Run Scripts、Bundled Release Readiness、distribution phase plan | 本地世界沙盘体验稳定，用户明确要求安装包或服务器在线体验 |
| 平台化边界 | 权限、对象存储、队列、认证、计费、配额、部署观测的本地边界文档 | 进入真实外部用户、多用户隔离或商业化试用时 |

## 3. 触发式增强规则

| 想做的事 | 先问 | 默认结论 |
| --- | --- | --- |
| 默认启用 hybrid vector | 是否有真实失败样本和 replay 证明 BM25 + ledger + aliases 不够？ | 没有证据就不默认替换 |
| 接 GraphRAG / Zep | 是否已有关系/因果/状态链真实错乱，并且 shadow/case/provider 边界证明收益？ | 没有证据就不接生产服务 |
| 扩 OpenAPI / typed client | 是否已有外部集成或桌面壳字段级契约需求？ | 没有需求就保留只读 contract |
| 做发行安装包 | 本地世界沙盘主流程是否已稳定、依赖安装是否成为真实用户阻塞？ | 未稳定前不做 |
| 做云端多租户/认证/计费 | 是否已经进入外部用户试用并需要数据隔离/成本结算？ | 未进入试用前不做 |
| 引入 LangGraph/OASIS/CAMEL | 现有 runner 是否被真实复杂样例证明无法表达？ | 未证明前不替换 |
| 做 LLM 语义评审 | 是否直接服务 Reviewer、整章风格润色或章节定稿质量？ | 只有服务作者链路时进入主线 |
| 动作执行 / 状态机 | 是否直接增强世界状态长期发酵和角色行动后果？ | 若只是机制实验则后置 |

## 6. 使用本文的正确方式

正确：

- 用户明确要求“检索/Graph/provider/发行/商业化/打包”时，用本文判断触发条件和边界。
- 当前世界沙盘主线碰到真实瓶颈时，用本文找可复用支撑能力。
- 写文档或接力时，用本文证明某支撑能力已收口，不重复开刀。

不正确：

- 从本文挑一个“还没做深”的支撑项作为默认下一刀。
- 把 Graph/provider/检索评测当作世界沙盘主线。
- 因为某项技术高级，就绕开角色行动、主观记忆、世界代偿和可读章节。
